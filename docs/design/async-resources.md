# Design: resources are loaded, not touched

> **Status: direction only, nothing implemented or authorised.** Written
> against the unmerged `origin/effect-brushes` (tip `30b6727b`,
> 2026-11-14); every path below points there. Three labels mark status:
> **OWNER**, the owner said it; **PROPOSED**, suggested in discussion and
> not confirmed; **UNVERIFIED**, a factual claim the code was not checked
> for. Nothing here upgrades a label. Names are working names. Builds on
> `image-brush.md`, whose decisions are referenced, not restated.

## Purpose

`image-brush.md` makes an image a future: it cannot be used until it has
loaded. This note records the wider direction that grew out of that:
every resource an application loads (images, fonts, later others) is a
future, the toolkit never blocks on one behind the application's back,
and an application has a visible structure for loading. It records what
the owner has said, what the code does today, and the open questions. It
is not a staged plan.

## What the owner has said

- **OWNER: loading is explicit.** An image has to be loaded before it can
  be used, unlike toolkits (Qt was the example) where pointing at an image
  resource hangs the UI for the load time. Fonts should probably work the
  same way. This gives applications a default structure: a resource
  loading step, and the UI shows when everything has loaded. Everything is
  deliberate, so no accidental hang can happen; the cost is more burden on
  the developer. Asked for an opinion, the answer given was agreement:
  resources are futures, and `wait()` on the load is the one deliberate,
  visible way to block.
- **OWNER: a default font is built in.** It is included in the binary and
  always available, covering basic characters: a freely available font,
  or one generated by the project.
- **OWNER: switching fonts is explicit.** Only the default font is
  immediately available. Any other font produces a future, which needs an
  explicit action to use; switching the font in a `then` handler is a
  very deliberate action, and that is fine.
- **OWNER, open direction: open the window after the load.** The owner
  would like to think about opening the window only once a load has
  happened, and expects it is already possible by adding the window when
  the `then` handler for the resources runs (*Where the code is* answers
  this).
- **OWNER, open direction: more embedded resources.** The owner wonders
  whether the toolkit should help embed more resources in the binary and
  offer load from memory, while "not sure if this is enough to consider
  the load immediate". Not a decision.
- **OWNER, open direction: async transformations.** There was once a plan
  for a function taking a future of a widget and a default widget, giving
  a widget that shows the default until the future resolves. The owner
  wonders which other transformations of that kind would be useful.
- **OWNER, decided in `image-brush.md`:** watched futures resolve on the
  thread pool, never the GL thread (*Fences*); the future-to-signal
  adapter lives in bq and is generic, its widget form in bqui; image
  creation has no synchronous form in the first version (*Making an image
  from pixels*); the render context moves to App and exists from App
  construction.

## Where the code is

Read at `30b6727b`; nothing was built or run.

**btl futures** (`src/btl/include/btl/future/`):

- `then` (`future.h:136-230`) runs its continuation on the thread that
  completes the future, or inline on the caller's thread when it is
  already ready (`futurecontrol.h:172-187`, `:214-224`). The continuation
  holds the new future only weakly (`future.h:166-172`), so dropping the
  future `then` returned drops the continuation.
- **Failure propagates.** A failed future rethrows when its value is read
  (`futurecontrol.h:79-80`); `then` catches anything its function or the
  read throws and fails its own future (`future.h:224-227`). `onFailure`
  (`future.h:119-131`) observes the `std::exception_ptr`. There is no
  pending/ready/failed value type; failure is the exception channel.
- `wait()` blocks (`future.h:291-294`); `get()` rethrows a failure;
  `cancel()` drops the control (`future.h:304-307`); `makeReadyFuture`
  makes a resolved one (`future.h:313-319`). `SharedFuture`
  (`sharedfuture.h:16`) is the form with several consumers.
- **Combining exists.** `whenAll` (`whenall.h:149-150`) joins
  heterogeneous futures into one; `merge` (`merge.h:108`) turns a vector
  of `Future<T>` into a `Future<std::vector<T>>`. In both the first
  failure fails the whole (`whenall.h:93-102`, `merge.h:57-67`). `join`
  (`join.h:17`) flattens a future of a future.
- **The pool** is a process-wide static (`threadpool.h:204-206`);
  `btl::async` posts to it (`async.h:13-21`).

**Fonts** (`src/avg`, `src/bqui`):

- `avg::Font` is made from a file path and a face index (`font.h:42`).
  The constructor loads **synchronously** through one static
  `FontManager` (`font.cpp:20-25`): `getFontImpl`
  (`fontmanager.cpp:265-294`) calls `FT_New_Face` on the path (`:281`)
  and throws `std::runtime_error` if it fails (`:283-284`). Loaded faces
  are cached weakly by path and face.
- **No load from memory.** `FT_New_Face` is the only face creation in
  `src/`; nothing calls `FT_New_Memory_Face` or `FT_Open_Face`.
- **No font is in the binary.** The repository carries
  `data/fonts/OpenSans-*.ttf` with an `Apache License.txt` beside them,
  read at a path relative to the working directory.
- **The theme names the font by path.** bqui's theme constructs
  `avg::Font("data/fonts/OpenSans-Regular.ttf", 0)` (`theme.cpp:62`,
  `:116`), so making a default theme loads a file synchronously and
  throws when the working directory lacks it. `Theme` has `getFont()`
  (`theme.h:34`) and no font setter; `label.cpp:31,51` and
  `textedit.cpp:50,150` read it.
- UNVERIFIED: whether FreeType reads glyph data lazily from the file
  after `FT_New_Face`, so that later text layout also touches the disk.

**Opening a window after the loop has started** (`src/bqui`):

- `App::addWindow` is documented as callable before and while the app
  runs, and lock-guarded so a worker thread may call it (`app.h:35-47`,
  `:105-111`). As read: it updates the window list under its lock, queues
  the mount under `pendingMutex_` and wakes the loop (`app.cpp:239-274`);
  the loop thread builds the window on its next sync
  (`app.cpp:393-414`). The wake is `PlatformBase::requestFrame`, an
  atomic flag and a run loop post (`platformbase.cpp:242-252`).
- So **adding the window from a `then` on a pool thread works today**, as
  read from the code; UNVERIFIED by a test.
- **`run()` with no window stops.** `run()` is `run(running)` with
  running meaning "the window list is not empty" (`app.cpp:314-321`). An
  application that loads first must either block before `run()` or pass
  its own running signal. UNVERIFIED that the stop happens before any
  frame; it follows from the condition.
- Today the render context is made inside the run (`app.cpp:362`), so an
  image cannot be made before `run()`; `image-brush.md` moves it to App.

**bq and other threads** (`src/bq`):

- **No future-to-signal piece exists.** `signal.h:19` and `shared.h:11`
  include the btl future header, but nothing in `src/bq` uses it.
- **Setting an input from another thread looks safe, as read.**
  `InputHandle::set` writes under the input's recursive mutex
  (`input.h:66-85`) and the update reads under the same mutex
  (`input.h:186-240`); observers fire outside the lock through
  `ObserveControl::fire` (`datacontext.h:33-42`). UNVERIFIED by a test or
  a sanitizer run.
- **The wake it causes is the weak link.** A window's observer sets an
  atomic and calls the ase window's `requestFrame`
  (`windowbridge.cpp:61-67`, `windowbridge.h:133`). On a generic window
  that writes a plain `std::optional` (`genericwindow.cpp:102-105`,
  `genericwindow.h:111`) before the platform's thread-safe wake; this is
  the racy request `image-brush.md` already makes safe in its frame
  request stage. `windowbase.cpp:75-76` states that `requestFrame()` is
  thread-safe; read against the generic window, that claim looks too
  strong.

## The model

- **PROPOSED: every loaded resource is a future.** Making one never
  blocks the caller; the value is usable once the future resolves. A
  failed load fails the future.
- **PROPOSED: one deliberate block.** `wait()` on the future is the only
  way to block, visible at the call site, for tools, tests and the
  startup case where blocking is the point. Nothing in the toolkit calls
  it for the application.
- **PROPOSED: only the default font is immediate.** Everything else,
  including resources embedded in the binary, goes through a future
  (*Embedded resources*).
- Continuations run on the pool (OWNER, `image-brush.md`); the way back
  to the UI is the bq adapter (*Transformations*).

The cost the owner named is real: every application writes a loading
step. The transformations below exist to keep that step short.

## Fonts

- **OWNER: a default font in the binary**, always available, with basic
  characters.
- **PROPOSED: which font.** A subset of an open font under Apache 2.0 or
  the OFL, embedded as a byte array and loaded through FreeType's memory
  load (`FT_New_Memory_Face`, unused today). Open Sans is already in the
  repository with an Apache licence file; whether its licence and size
  suit embedding is UNVERIFIED. "Basic characters" needs a definition:
  ASCII, or Latin-1.
- **PROPOSED: a Meson option turns the embedded font off**, for
  applications that ship their own; the theme then has no immediate font,
  and how it behaves without one is an open question.
- **PROPOSED: embedded is "always available", not "free".** Load from
  memory still parses the face; only the default font is treated as
  immediate, because it is made once, early, by the toolkit.
- **OWNER: other fonts are futures**, and switching to one happens in a
  `then` handler. Today that needs a way to change the theme's font, which
  does not exist (`theme.h:34`).
- **PROPOSED: the theme's default stops naming a path.** The working
  directory dependence in `theme.cpp:62` goes when the default font is
  embedded.

## Embedded resources

The owner's question is open. PROPOSED, for discussion:

- **Load from memory for every resource type**, as an entry point beside
  the file one. It still returns a future: parsing a font or decoding an
  image costs time, and the owner doubted that embedding makes a load
  immediate.
- **A build helper** (Meson plus a small Python script) that turns files
  into byte arrays, so applications do not hand-write them.
- **Optionally decode at build time**, so an embedded image is raw pixels
  and loading it is only the upload. The upload is still asynchronous
  (`image-brush.md`, no synchronous form), so this saves the decode, not
  the future.

## Transformations

All PROPOSED except where marked. The first two are already in
`image-brush.md` and are restated here only as part of the set.

- **A future becomes a signal of an optional value** (bq, generic; OWNER
  in `image-brush.md`). Empty until the future resolves.
- **A future of a widget and a default widget give a widget** (bqui;
  OWNER in `image-brush.md`, the owner's earlier plan).
- **Latest of a changing request.** A signal of requests gives a signal
  of the newest finished result; a result for a request that has since
  changed is dropped. This is the font switch and the avatar that follows
  a selection.
- **Explicit failure.** A result that is pending, ready or failed, so a
  failed load shows something the application chose rather than nothing.
  btl carries failure only as an exception (*Where the code is*); the
  signal side would turn it into a value.
- **Combine loads.** `whenAll` and `merge` exist in btl; the gap is
  ergonomics for "load everything, then show the UI", for example a named
  set of resources resolving into one value the UI is built from.

## Application shapes

Sketches, not real signatures.

**(a) Load everything, then open the window.** The window is added in a
`then` on the pool, which `addWindow` allows (*Where the code is*). The
run needs a running signal of its own, since `run()` with no window
stops at once.

```cpp
App app;
whenAll(loadFont(...), loadImage(context, ...))
    .then([&](Font font, Image logo)
    {
        app.addWindow(window("Main"), mainUi(font, logo));
    })
    .detach();
app.run(untilQuit);
```

**(b) Open at once, fill in as loads finish.** The window shows
placeholders; each resource arrives through the bq adapter.

```cpp
auto logo = signalFromFuture(loadImage(context, ...)); // optional<Image>
app.addWindow(window("Main"), header(logo, placeholderIcon()));
app.run();
```

**(c) The deliberate block.** For tools and tests; the `wait` is visible.

```cpp
auto font = loadFont(...);
font.wait();
```

## Open questions for the owner

Each with a proposed default.

1. **Which default font, and how many characters?** Default: a subset of
   Open Sans (already in the repository), Latin-1.
2. **Can the embedded font be turned off?** Default: yes, a Meson option,
   on by default.
3. **Is any embedded resource other than the default font immediate?**
   Default: no; load from memory returns a future.
4. **Does the toolkit offer build-time embedding?** Default: a small Meson
   helper, later; load from memory first.
5. **How does an application wait to open its first window?** Default: a
   running signal it passes to `run()`; a helper that ties the run to a
   future is a later convenience.
6. **Is failure a value on the signal side?** Default: yes, the adapter
   gives pending, ready or failed; the optional form stays for the simple
   case.
7. **How is the theme's font changed?** Default: a theme setter used from
   the UI after a font future resolves, not a font signal inside the
   theme.

## Non-goals

- Blocking loads hidden inside the toolkit, and lazy loading on first use.
- A resource manager or cache beyond what each loader keeps.
- File decoders inside avg (`image-brush.md`).
- Network loading, hot reload and resource packs.
